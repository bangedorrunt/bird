# Writing

Two verbs write: `tweet` and `reply`. Both need a session, both accept media (see
[Media](./media.mdx)), and both refuse to send an empty post.

## Post a tweet

```sh
bird tweet --text "hello from bird" \
  --auth-token "$TWITTER_AUTH_TOKEN" --ct0 "$TWITTER_CT0" \
  --web-bearer "$BEARER" --gql-features "$FEATURES" \
  --op-create-tweet "$CREATE_TWEET_QUERY_ID"
```

A bare word after the verb is the text, so this is the same command:

```sh
bird tweet "hello from bird" --auth-token … --ct0 … --web-bearer … --gql-features … --op-create-tweet …
```

## Reply to a tweet

```sh
bird reply 1234567890 --text "a reply" --auth-token … --ct0 … --web-bearer … --gql-features … --op-create-tweet …
```

The argument is a tweet id or a whole url; the request only ever carries the
extracted id. An argument with no id in it is refused with exit code `2` before a
request exists, so a typo never becomes an empty `in_reply_to_tweet_id` sent to X.

## Text from a file

`--text-file` fills the text when the command line did not carry any. It is a way
to avoid quoting, not an override: an explicit `--text` wins.

```sh
printf 'a post read from a file' > post.txt
bird tweet --text-file post.txt --dry-run --json
```

A `--text-file` the run cannot read is an error naming the path and the reason,
with exit code `2`. A config file that cannot be read is the one failure the run
shrugs off, because a missing config is not a configuration error.

## An empty write is refused

```sh
bird tweet --auth-token … --ct0 … --web-bearer … --json
```

```json
{"ok":false,"error":{"id":"usage","message":"tweet has nothing to send","hint":"give it its text, or --text-file PATH"},"status":0,"body":"","notes":[]}
```

Exit code `2`. The check happens after the text file has been merged in, so the
text may be exactly what the file held; what it refuses is a post with no text and
no media at all. A media-only tweet is a real post, so `tweet --media shot.png`
is wordless, not empty.

## Look before you send

`--dry-run` prints the request the run *would* have sent, and sends nothing. The
description is the data the interpreter would act on, including the `curl` argv,
so it can be compared with a real run rather than trusted:

```sh
bird tweet --text "hello" --auth-token … --ct0 … --web-bearer … \
  --gql-features "$FEATURES" --op-create-tweet "$CREATE_TWEET_QUERY_ID" --dry-run --json
```

```json
{"ok":true,"verb":"tweet","status":0,"data":{
  "method":"POST",
  "url":"https://x.com/i/api/graphql/<create-tweet-query-id>/CreateTweet",
  "headers":[{"name":"authorization","value":"Bearer …"},{"name":"x-csrf-token","value":"…"},{"name":"cookie","value":"auth_token=…; ct0=…"},{"name":"content-type","value":"application/json"},{"name":"x-twitter-active-user","value":"yes"},{"name":"x-twitter-auth-type","value":"OAuth2Session"}],
  "body":"{\"variables\":{\"tweet_text\":\"hello\",\"dark_request\":false},\"queryId\":\"…\",\"features\":{}}",
  "parts":[],
  "timeout_ms":15000,
  "curl":["curl","-sS","https://x.com/i/api/graphql/…/CreateTweet","-X","POST","-H","authorization: Bearer …","--max-time","15","-d","{…}","--write-out","%{http_code}"]
},"notes":[]}
```

The `curl` array is the whole command line, program included, so it can be pasted
into a shell to inspect the request by hand. Nothing in the text is passed through
a shell: `--text 'a; rm -rf /'` stays one literal argument, which is why the text
of a tweet cannot become a command.

## A successful write

```json
{"ok":true,"verb":"tweet","status":200,"data":{"data":{"create_tweet":{"tweet_results":{"result":{"rest_id":"5150","legacy":{"full_text":"hello from bird"}}}}}},"notes":[]}
```

Exit code `0`. On a terminal the same run prints the data indented instead of the
envelope; pass `--json` when a script is reading, rather than relying on the
rendering being guessed right.

## Failures worth knowing

| what happened | exit | `error.id` |
| --- | --- | --- |
| no credentials at all | 3 | `auth` |
| a session with no `--web-bearer` | 2 | `usage` |
| the session is expired (401) | 3 | `auth` |
| X refused the account (403) | 3 | `auth` |
| rate limited (429) | 5 | `rate_limited` |
| `curl` could not connect or timed out | 6 | `network` |
| X answered 5xx | 7 | `upstream` |

X's own words are kept in `body`, and `curl`'s own words (a host that does not
resolve, a timeout) arrive in `notes`, so a connection that never happened is not
reported as an empty response.
