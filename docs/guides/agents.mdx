# Agents

Everything an agent needs is one envelope on stdout, one exit code, and a schema
it can read before it types anything.

```sh
bird schema --json | jq '.data.verbs, .data.flags, .data.exit_codes'
```

## Output is an envelope, or prose, never both

One JSON envelope goes on stdout when `--json` is passed, when `BIRD_JSON=1` is
set, or when `TERM` is empty or `dumb`. Otherwise a terminal gets the payload as
prose — a read's tweets as one block each, everything else indented — and notes go
to stderr so a warning never lands in the middle of the data a script is reading.

**`TERM` is a proxy, not a fact.** Bend has no `isatty`, and the process that runs
`curl` is given pipes, so nothing can ask whether this process's stdout is a
terminal. A script that pipes `bird` while `TERM` is set in the environment gets
the terminal rendering. Pass `--json` and do not rely on the detection.

## The success envelope

```json
{"ok":true,"verb":"search","status":200,"data":{"…":"X's payload"},"notes":[]}
```

| field | meaning |
| --- | --- |
| `ok` | `true` on success, `false` on failure. |
| `verb` | The verb that ran. Absent on a usage error, because the command line may not have named one yet. |
| `status` | The HTTP status, or `0` when no request was made. |
| `data` | What the run fetched: for `read`, `replies`, `thread`, `search` and `mentions` it is `{"tweets": […]}` with X's envelope left behind, for `whoami` one profile, and `null` for a run that did something rather than fetched something (a write, `check`). |
| `notes` | Warnings, each a line. `curl`'s own words for a connection that never happened arrive here. |

## The failure envelope

```json
{"ok":false,"error":{"id":"rate_limited","message":"Rate limit exceeded","hint":"X is rate limiting this account: back off before retrying","retryable":true},"status":429,"body":"Rate limit exceeded","notes":[]}
```

`error.id` is stable API: `usage`, `auth`, `not_found`, `rate_limited`,
`network`, `upstream`, `internal`. Branch on it, not on prose. `body` keeps X's
own answer, which is often the useful part of a 4xx.

`error.retryable` is `true` for exactly `rate_limited`, `network` and `upstream`,
so a caller that wants to back off and retry reads one boolean instead of keeping
its own copy of that table. Nothing in a run retries by itself.

One case vetoes the table, and it is the one that costs a duplicate post: a request
that was **sent** whose answer never came back. `tweet` and `reply` are the only two
verbs that change anything, and a `curl` timeout (28), an empty reply (52) or an
answer that died part way (56) all mean X may have accepted the post. Those answer
`"id":"network"` with `"retryable":false` and a hint saying to check the account
before retrying:

```json
{"ok":false,"error":{"id":"network","message":"curl timed out","hint":"curl exit 28: the request was sent and the answer was lost; check the account before retrying, the post may already be there","retryable":false},"status":0,"body":"","notes":["curl: (28) Operation timed out after 1000 milliseconds with 0 bytes received\n"]}
```

The same status on a read is an ordinary retryable failure. `curl` 6 and 7 (could
not resolve, could not connect) mean nothing was sent, so those stay retryable for a
post as well: the rule is about the request, not about the status.

## Exit codes

| 0 | 2 | 3 | 4 | 5 | 6 | 7 | 1 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| ok | usage | auth | not found | rate limited | network | upstream | internal |

The exit code and `error.id` agree, so a shell can branch without reading either
output shape.

## Check before you act

Three ways to see what a run will do without it doing anything:

```sh
bird tweet --text hi … --dry-run --json     # the request it would send, and nothing else
bird read 1234567890 --fixture tweet.json --json  # answer from a file, through the live path
bird check --json                           # what the settings resolved to; sends nothing
```

`--dry-run` prints the request as data, including the exact `curl` argv, so a
human can paste that command into a shell and inspect it by hand. A media write
prints a plan instead (see [Media](./media.mdx)).

## Reading work back out

- A read answers with the tweets, not with the 119 KB they arrived in:
  `.data.tweets[]`, each with `id`, `text`, `lang`, `created_at`, `author`,
  `metrics`, `media`, `urls`, `quoted` and `in_reply_to`. `--raw` answers with the
  body X sent instead. See [Reading](./reading.mdx).
- `--count` is 1..50 for `search` and `mentions` (one page each) and 1..500 for
  `bookmarks`, whose count is a total read across pages; default 10. A value
  outside its verb's range is refused with exit 2, never rounded down, so a short
  answer is always visible in `notes`.
- A tweet id or url is accepted anywhere a target is wanted; the request carries
  the extracted id, never the whole url.
- A body that is not JSON is kept in `body`, with a note saying why `data` is
  null, so an HTML error page is not thrown away.
- A media write that fails part way through names the media ids already uploaded
  in `notes`, because those uploads are still good: a retry can reuse them
  instead of sending the same bytes again.

## Refusals are named

An unknown flag, a flag without its value, a verb without its argument, a stray
word, a config key the flag table does not know, a content flag in a config file,
a target with no id in it, and a media write asked to answer from `--fixture` are
all refused by name with exit code `2`. An agent that misspells a flag and gets
silence cannot tell that from a request that asked for nothing, so silence is
never the answer.
