# Reading

Every verb here reads, and none of them works from `--web-bearer` alone: X's
GraphQL API wants the session, and the API-key backend takes reads as well.

| verb | what it fetches |
| --- | --- |
| `read <tweet-id\|url>` | One tweet. |
| `replies <tweet-id\|url>` | The replies to it. |
| `thread <tweet-id\|url>` | The whole self-thread. |
| `search <query> [--count <n>]` | Recent tweets matching the query. |
| `bookmarks [--count <n>]` | The signed-in account's saved bookmarks. |
| `whoami` | The signed-in account. |
| `check` | What the settings resolved to. Sends nothing. |

```sh
bird read https://x.com/someone/status/1234567890 \
  --auth-token "$TWITTER_AUTH_TOKEN" --ct0 "$TWITTER_CT0" \
  --web-bearer "$BEARER" --gql-features "$FEATURES" \
  --op-tweet-detail "$DETAIL_QUERY_ID" --json
```

## A tweet id, from an id or a url

The argument is either the id or a whole url, and the request only ever carries
the extracted id — what you pasted is never forwarded. A url is read for
`/status/<digits>`, so

```sh
bird read https://x.com/someone/status/1234567890 --dry-run --json
bird read 1234567890 --dry-run --json
```

describe the same body:

```json
"body":"{\"variables\":{\"focalTweetId\":\"1234567890\",\"includePromotedContent\":false,\"withBirdwatchNotes\":false,\"withVoice\":false},\"queryId\":\"…\",\"features\":{}}"
```

The three extra variables are not decoration: X validates the variables before it
runs anything, and without them `TweetDetail` answers 422 naming the first one
missing. They are what a working read costs.

## A target with no id in it is refused

If nothing in the argument can be read as an id, the run stops with exit code `2`
rather than sending an empty `focalTweetId`:

```sh
bird read abc --auth-token … --ct0 … --web-bearer …
# exit 2: "that is not a tweet id, and none can be read out of it: abc"
```

Digits are what the extraction keeps, so a plain id, a url with `/status/<id>` in
its path, and a share url with a query string (`…/status/99887766?s=20&t=abc`) all
work; a handle, a word, or a url without a status path does not, because it would
spend a round trip to learn what is knowable locally.

## Count

`--count` applies to `search`, `mentions` and `bookmarks` and is clamped to **1..50** (the
default is 10). `--count 0` becomes 1, `--count 999` becomes 50. It is read from
the item list rather than the verb, so it counts whether it was written before or
after the verb it belongs to — and a value the program cannot read is refused
rather than quietly replaced by the default.

## What a read answers with

X wraps one tweet in about 119 KB of its own bookkeeping — timeline entry ids,
cursors, display options, the author's whole profile blob, the client's feature
flags — and the text sits six levels down inside it. That walk happens once, in
`src/tweets.bend`, so a read answers with the tweets rather than with the
envelope they arrived in:

```json
{"ok":true,"verb":"read","status":200,"data":{"tweets":[{"id":"1234567890","text":"a tweet","lang":"en","created_at":"Sat Oct 10 00:00:00 +0000 2026","author":{"id":"77","handle":"someone","name":"Some One","verified":false,"avatar":"https://pbs.twimg.com/profile_images/x_normal.jpg"},"metrics":{"replies":3,"retweets":4,"likes":5,"quotes":6,"bookmarks":7,"views":12345},"media":[{"type":"photo","url":"https://pbs.twimg.com/media/one.jpg","alt":null}],"urls":[],"quoted":null,"in_reply_to":null,"article_title":null}]},"notes":[]}
```

| field | what it holds |
| --- | --- |
| `id` | The tweet's id. |
| `text` | The whole text. A long post answers with the text from `note_tweet`, not the truncated line X puts beside it, and a post that is an X Article answers with the article's body: its draft.js blocks folded to text, with headings, lists and quotes keeping their markers. |
| `lang`, `created_at` | The language and the timestamp; `null` when the response did not carry one. |
| `author` | `id`, `handle`, `name`, `verified`, `avatar`; `null` when there is no author to find. |
| `metrics` | `replies`, `retweets`, `likes`, `quotes`, `bookmarks`, `views`. A count X did not send is `null`, which is not the same answer as `0`. |
| `media` | One entry per attachment: `type`, `url`, `alt`. |
| `urls` | One entry per link: `url`, `expanded`, `display`. |
| `quoted` | The quoted tweet, in this same shape, one level deep. A quote of a quote is not followed. |
| `in_reply_to` | The id of the tweet this one answers, `null` when it answers none. |
| `article_title` | The title of the article the post carries, `null` when it carries none. The body is what `text` holds. |

```sh
bird search rust --count 5 … --json | jq -r '.data.tweets[].text'
bird read 1234567890 … --json | jq -r '.data.tweets[0].author.handle'
```

`read` asked for one tweet and X answers with the conversation around it, so it
keeps the tweet that was asked for. `replies`, `thread`, `search`, `mentions` and
`bookmarks` asked for a list and keep every tweet X sent, in X's order. `whoami` answers with
one profile in the same spirit (`id`, `handle`, `name`, `verified`, `avatar`,
`bio`, `followers`, `following`, `tweets`, `location`, `created_at`).

## Bookmarks

`bookmarks` reads the saved bookmarks of the signed-in account. It is a GraphQL
read like the rest and folds the same way, and it is the one verb whose operation
is not in X's client bundle: the bundle carries the operations `login` captures
for everything else, but the bookmark timeline moved out of it. So
`--op-bookmarks` defaults to a recorded query id rather than the operation's name,
`login` leaves the setting out of the cache rather than writing it empty, and a run
that starts answering `Query not found` wants a fresh id:

```sh
bird bookmarks --count 20 --json
bird bookmarks --op-bookmarks "$FRESH_ID" --json
```

## A terminal gets the tweets

A person at a terminal never passes `--json`, and a wall of braces is not what a
terminal is for. So the tweets are printed as one block each: the head, the text,
one line per attachment, the quote, the reply target, and a last line of the id
and the counts X sent.

```sh
bird read 1234567890 …
```

```
@replier · A Replier · Sat Oct 10 00:00:00 +0000 2026
the whole long post
media photo https://pbs.twimg.com/media/one.jpg alt: alt one
quoting @quoted: the quoted tweet
in reply to 199
id 200 · replies 3 · retweets 4 · likes 5 · quotes 6 · bookmarks 7 · views 12345
```

A field X did not send drops out of its line rather than leaving an empty slot,
and an answer holding no tweet says `no tweets` instead of printing nothing.

## Seeing the envelope again

`--raw` is the way back to the body X sent, for the times the fold has thrown away
something you wanted:

```sh
bird read 1234567890 … --json --raw | jq -r '.data.data.tweetResult.result.legacy.full_text'
```

Two `data`s there: the outer one is the envelope's payload, the inner one is X's
own.

## Answering without a network

`--fixture PATH` answers the run from a file, through the same fold a live
response takes, so a fixture cannot drift from a real run:

```sh
bird read 1234567890 --fixture tweet.json --json
```

That is the whole request path minus the socket: the body is parsed, the status
reported is the one a real 200 would give, and the error path is the same one a
live 404 takes. `--dry-run` is the other half: it prints the request that would
have been sent instead of answering it.

## Failures

The status X returned is kept in `status` even when the run fails, so a 404 reads
differently from a 500 and from a request that never left:

```json
{"ok":false,"error":{"id":"not_found","message":"{\"errors\":[{\"message\":\"No tweet found\"}]}","hint":"the tweet may be deleted, or the id may be wrong"},"status":404,"body":"{\"errors\":[{\"message\":\"No tweet found\"}]}","notes":[]}
```

A failure with no request behind it — a usage error — reports `status` 0, which is
the honest answer there. A body that is not JSON is not thrown away: it is kept in
`body` and a note says why `data` is null. `error.retryable` says whether trying
again unchanged is sensible, so a caller does not have to keep its own copy of the
status table.
